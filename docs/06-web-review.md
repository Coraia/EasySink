# Web 设计与实现评审 · 2026-09-11

结论：保留产品方向、FastAPI/SQLite 和候选生成与个人筛选分离的思路；重做阅读状态、内容定位、插件生命周期，并修订标注策略。当前应定位为可试用原型，不能继续用“所有功能都 OK”描述。

本轮限定 Web，不评估小程序、支付、商业化和旧合规结论。未修改应用代码、用户数据库或插件开关。上一轮同一份代码的基线是 37 个 pytest 用例通过；本轮使用临时数据库、合成 EPUB、模拟模型和 Node VM 定向反例。Node VM 使用简化 DOM，因此属于函数级验证，不是浏览器视觉或端到端验收。没有调用真实模型，也没有重新测试真实浏览器朗读与移动端触摸。

**优先级约定**：P1 是应在下一轮日常体验前处理的错误、丢失或核心承诺失效；P2 是下一阶段的质量与可靠性工作。设计变更是建议，尚未实施。

**需要推翻的四个设计假设**

1. “词汇层完全不用上下文”。`lexicon.py:46` 只取首行词典释义。例如当前 `redistricting` 返回“[美]重划学区”，放进选举文章会误导；`bank` 一律给“银行,堤,岸”，仍要求读者自己消歧。词典适合提供义项与词频，语境选义应由规则、短语识别和按需模型共同完成。对语义不确定的结果应提供可展开候选或低置信提示，不能因为标得少就视作高质量。
2. “宁可漏标，固定密度优先”。稀有不等于决定理解，熟词僻义和短语可能比生僻名词重要。改为优先覆盖理解障碍，在给定阅读模式下控制视觉负担。保留密度调节，但将其定位为偏好；必要帮助可展开。每篇只标一次也应允许跨章节或词义改变时再次提示。
3. “Token ID 等于正确定位”。编号只解决坐标引用，不证明模型选中了正确语义。当前 `tokenize.py:53` 发给模型的词流还丢掉标点；实测 `Let's eat, Grandma!` 与 `Let's eat Grandma!` 的模型输入完全一致。模型输入必须保留原句标点、段落、引用与代码块。坐标校验之外需要语义质量验收。
4. “拆成 15 个文件就能随时移除功能”。当前依赖关系和生命周期没有显式契约；核心 `store.py:181` 又直接列举插件表名。应把所有功能共用的内容模型、定位、保存、任务管理留在核心，再让用户选择功能模块。开关是体验入口，代码独立需要另外验收。

**阅读器与内容模型建议重做**

当前内容仅为一整段字符串，EPUB 的标题、强调、列表、代码、脚注链接、图片被剥离。书签记录整页滚动比率；同一比例随字号、窗口高度、译文栏和文末笔记变化而指向不同内容。笔记只保存摘录字符串，没有精确位置，重复句子也无法区分。

建议建立 `Book → Chapter → Block`，保留经过清理的语义结构和原始资源。用内容版本、块 ID、字符偏移和摘录上下文定位。注释、笔记、书签、续读、搜索结果、朗读进度、译文对齐共同引用这个坐标，显示比例仅作为进度信息。历史字符串资料可以先转成段落块，不必一次迁移全部旧功能。

摘录上下文和字符位置可参考 [W3C Web Annotation selectors](https://www.w3.org/TR/annotation-model/#selectors)。规范中的 TextQuoteSelector 使用 exact、prefix、suffix 区分重复内容，TextPositionSelector 提供字符范围；本项目仍需自行处理版本与 DOM 映射。

**前端建议重构范围**

- 将路由、服务端数据、读者偏好、阅读位置和编辑草稿分开管理，避免全局 `state.doc` 加 `innerHTML` 作为唯一状态。
- 插件具有挂载/卸载、依赖、数据版本和错误状态。插件应通过受控能力接口读写内容，不能任意操作全局 DOM 和数据库。
- 默认主路径只保留书架/导入、继续阅读、阅读设置；笔记、译文等按上下文展开，实验室保留全部 15 项供体验。功能可以保留，导航不必全展开。
- 词汇短注保留行内；复杂句式与文化解释允许段内展开或侧栏。呈现形式按解释长度决定，不必把所有内容都塞进括号。
- 改密度、换主题或开译文后，保持同一句原文在视口中的位置；保存状态包含进行中、成功、失败重试，并支持撤销。
- 档案的独立并发 PATCH 存在顺序覆盖风险，且某项先完成时会把其他仍待保存的状态显示为“已保存”。需要队列或字段版本，不依赖请求返回顺序。

这涉及阅读器壳层和状态管理的重做。是否采用组件框架是次级选择；FastAPI、SQLite、词库资源和现有可用 API 可继续保留，无需为此引入微服务。

**可读性不能靠把帮助文字变淡解决**

`web/style.css:86` 注释固定 11px，默认 #9a9a9a 对 #fffdf8 的计算对比度约 2.77:1。普通小字的 WCAG AA 参考线为 4.5:1，见 [W3C 对比度说明](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)。注释承载关键信息，应提供足够对比度和相对字号。夜间主题的 `.bubble` 仍白底，而正文文字颜色继承夜间浅色，也需统一修正主题变量。

另外：注释是可点击 span，没有键盘焦点和按钮语义；状态更新没有实时无障碍提示；长按查词不处理 touchmove/touchcancel，可能和选字或滑动冲突。上述均由代码检查发现，移动端实际发生频率需浏览器补验。

**翻译、导入和模型增强需要任务模型**

目前翻译在单次请求中逐块调用模型，只在整章全部完成后写入；超时缺乏断点。`_chunks` 的 1400 字符目标不拆超长单段，实测 10000 字符单段仍输出 10000 字符块。没有整书任务、部分完成状态、取消、失败重试或术语上下文。当前“翻译书”应准确标为“当前章节译文对照”。

导入的 async 接口内部执行同步分析和模型调用，会占用事件循环；书和章节逐条提交，失败可能留下部分记录。文件大小检查发生在读完整个上传之后，没有独立解压总量预算。建议导入先解析并校验目录，再持久化内容；标注与翻译进入可持久化任务。自用版本可先用 SQLite 任务表加单个后台 worker，任务进度通过轮询呈现。

模型内容应有成功、未配置、失败和待处理状态，阅读正文无需等待完整 AI 处理。翻译记录按章节/块及原文版本保存，允许逐块重试；“重新生成”保留旧译文版本。缓存可以复用，但必须对模型与解析规则版本敏感。

**登录与存储范围应明确**

当前 auth 只允许第一个账号注册，profile 是 id=1 的单例，文档、笔记无 owner 字段，适合本机实例锁。Web 自用阶段可以保留并明确命名。若未来允许多人访问，再把鉴权作为部署策略、增加账户归属和隔离验收；不能直接把注册限制去掉就宣称支持多用户。当前会话没有服务端过期、找回及登录限速，公网部署前另作审查。

SQLite 仍可保留，但后续迁移要有 schema 版本、备份/恢复验证和明确事务边界。目前跨请求共享单连接及辅助方法每次自动 commit 的方式不适合直接扩展复杂并发任务。移除功能默认应保留数据，彻底清除需另设动作；删除书籍附带删除学习笔记的现有行为也值得改为回收站或导出后清理。

**验收标准需要重写**

当前仓库测试以 Python 单元/API 为主；`test_frontend_plugin_files` 只验证脚本存在、HTTP 200 与文本片段，不执行 JavaScript。37 项通过只能覆盖这些断言；本轮新增反例恰好说明验收缺口。

“0 次查词 + 密度 ≤5%”也不足以证明产品有效：错译无人察觉、用户跳读和没读懂，都可能得到漂亮数字。建议分别验收：

- 正确性：语境释义正确、关键理解障碍覆盖；按词汇、习语、语法、文化分开观察。
- 个人化：误标/漏标的真实个人基准；保留独立材料，避免只优化固定样本。考纲数字只作为初估。
- 阅读效果：同等材料下的理解题表现、完成率和主动中断次数；“更顺畅”需要本人体验。
- 状态可靠性：反馈后跨页/刷新仍有效；改设置不丢草稿；请求乱序不覆盖当前页面；多篇阅读日志互不串数。
- 内容完整性：导入章节总数对齐，无静默截断；改排版、切译文后定位仍命中相同原句。
- 插件隔离：所有插件关闭时内核可用；声明依赖后逐项关闭；从清单/代码移除并在新库启动；失败插件不破坏阅读与保存。
- AI 故障：未配置、慢响应、超时、格式错误、断网、重试和版本升级都可恢复；模拟测试与真实模型质量验收分列。

长期使用还需要稳定启动入口、健康检查、明确日志位置与异常退出提示。上文已有多次端口拒绝连接记录；本轮未重新启动服务，也没有新的退出原因证据，不能把历史进程消失归因于电脑休眠。
