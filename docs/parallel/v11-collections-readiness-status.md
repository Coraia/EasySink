## Failure classes recorded before implementation / targeted checks

- A state request may stall before headers or while reading JSON. An optional `prepare-reading` await must settle after a modest deadline, expose unavailable state and let source rendering proceed.
- Fetch/body work can resolve or reject after timeout, abort or replacement. Such obsolete results must not publish state, change seed, apply overlays/marks, emit layout events or overwrite a newer retry. Request-scope cancellation and generation/source-version guards must remain effective.
- A fast successful initial request must still apply annotations before source indexing and marks before live/detached paint. A slow request must not turn into a silent background annotation update after indexing.
- A neighboring prepared range may time out yet finish pagination with fallback source. Its handoff must carry the same unavailable state rather than retrying before adopting already measured pages. An explicit retry on the mounted reader must use the normal annotations-change reflow when feedback changes.
- Navigation/plugin disposal or replacement reads must settle awaiting work promptly even if the underlying request ignores cancellation; timers and abort listeners must be cleaned up. Superseded/aborted work must not report an unrelated error in the next reader.
- Retries and subsequent refreshes must also be bounded. Error/unavailable controls must remain visible, allow an intentional retry, and never claim records loaded after failure. Body reading must continue; no automatic polling/retry loop.
- A document/version change during a request must not accept that response for the new source. Existing historical-version filtering must remain intact. Failure after a prior success must not clear persisted records or silently rewrite current pagination.
- Syntax/import/format checks only provide source evidence; actual time-to-body, event ordering, warm-range adoption and UI recovery remain parent browser acceptance.
- Prefetch extension (recorded before implementation/checks): `prepare-document` must return synchronously, start only one handled state read per preparation, and overlap rather than await document/plugins/profile. The 1.5-second deadline starts at prefetch creation; consuming a failed prefetch must not restart that allowance or silently retry.
- A preparation may be abandoned, reused for another document, superseded or bypassed by a handoff seed. Its result must never publish independently, leak an unhandled rejection, or apply to the wrong document. Controller reload consumes at most one matching prefetch; later explicit retries start fresh bounded reads.
- Fast prefetch completion can precede document arrival. It must remain inert until the matching controller applies it before first indexing. Scope/version/generation guards, failed warm-packet handoff and seed priority must remain intact. A cold app with no installed prefetch hook must retain bounded ordinary loading.

## Repair and exact integration contract

- `STATE_READINESS_MS = 1500` bounds each state read, including prefetch, initial readiness, explicit retry and subsequent mutation refresh. `startStateRead()` races the complete store read (including JSON) against a deadline and request-scope abort. The deadline rejects before aborting the transport, so a body reader that swallows cancellation cannot convert timeout into a successful empty state. A losing read has no publication continuation. Read errors are immediately converted to a handled `{error}` result, including when no controller ever consumes a preparation.
- The local request is disposed and its timer/listener cleared in `finally`. A replacement read increments generation before cancelling the old request. Controller/reader abort, request abort, obsolete generation and changed document ID/version prevent publication. Abort/replacement ends the wait without publishing a failure into another reader. Source/overlay version filtering is unchanged.
- Successful initial readiness still publishes before `prepare-reading` returns, so the parent applies annotations before `indexSource` and paints live/detached marks as before. Successful seeds remain the raw `{items, feedback}` API object. Seeds take priority over all prefetch results: an already-started speculative prefetch is cancelled/discarded and no controller state read is started for the seed handoff.
- Failure sets `loaded=false`, retains the accepted state (initially empty) and exposes `error`. It does not call the overlay/painter or trigger a reflow. The UI shows an unavailable toast with an explicit retry and a persistent error/retry control in the collection panel. The existing word-card error/retry remains usable. The panel follows state events, including failures after the panel was already open; `loading` disables repeated panel retries. There is no automatic polling/retry timer.
- **Client-only failure seed:** `reader.collectionsSeed = {items, feedback, collectionsUnavailable: {doc_id, version, message}}`. These items/feedback are the exact fallback state used to prepare the packet, not fabricated saved records. Parent already passes this object unchanged to the incoming reader. The plugin recognizes the failure marker, checks document/version and restores `loaded=false/error` without another prepaint request. This preserves the annotations under which the warm packet was measured. An incompatible failure seed fails closed. The marker is never sent to the backend or written into user records.
- Explicit successful retry after `read` mounts uses the existing publication path: marks repaint/invalidate paint, changed effective feedback emits `annotations-change` for the parent's source-based reflow. A word-card retry that finishes in the gap after indexing but before `read` mounts is rejected as temporarily unavailable instead of silently changing an unmounted overlay. Legacy readers that create the controller after layout retain their existing initial-reflow path.
- `reload() -> Promise<void>` and `ready` still settle optional failures rather than throwing through preparation. `state`, `loaded`, `error`, `paint()` and `applyAnnotations()` retain their existing meanings; `loading` is a new read-only UI state. Bounded readiness itself needs no parent edits; optional prefetch requires only the generic app wiring below. No API endpoint, CSS, persisted schema or store change is needed. The 1.5-second deadline bounds this optional request, not unrelated document/assist/font loads or browser scheduling/render time.

## Optional prefetch hook — exact parent wiring

- The parent invokes `ctx.run('prepare-document', preparation)` before its document/plugins/profile `Promise.all`, where `preparation = {docId: Number(id), scope}`. Assign that same object to `reader.preparation` before `reader.mount()`. Parent owns these generic app additions; this contributor did not edit app or Reader.
- The plugin's `prepare-document` callback is a **synchronous function returning undefined**. It only starts the production state GET and stores `preparation.collectionsPrefetch`; it neither awaits the request nor publishes state, creates a reader, paints, or attaches DOM listeners. Repeated invocation for the same live preparation does not duplicate its request. No installed plugin on cold first app load means no prefetch field; ordinary bounded loading remains available.
- `collectionsPrefetch` is plugin-private `{docId, scope, result, isCurrent}`. `result` resolves to `{payload}` or `{error}`; parent must not await it. The transport is linked to both preparation scope and plugin store scope, with its own 1.5-second deadline starting at hook invocation. Completed successful reads clear the timer. Consuming a pending read waits only its remaining time; consuming a timed-out read reports failure immediately without restarting the allowance.
- `createController` takes and deletes the private field once. Only the same numeric document ID and an active preparation/plugin owner can be used by its first `reload()`. A mismatched/cancelled preparation is disposed and discarded; that controller uses its normal bounded read. Later retries always start a fresh read. A preparation cancelled after network completion is still rejected by the owner validity check. Reader disposal or a replacement reload cancels a consumed, still-pending prefetch.
- There is no autonomous prefetch publication. Matching consumption still checks the controller/reader scope, request scope, reload generation and the loaded document's ID/version before publishing ahead of indexing. Handoff seed priority applies equally to success and unavailable seeds, so a newer speculative success cannot silently change an already measured fallback packet. Generic route prefetch may already have issued a GET before the handoff is known; it is cancelled/discarded rather than consumed.
