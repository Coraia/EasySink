## 二、微信小程序的六条硬约束

### 1. 个人主体无法开通微信支付（致命）

微信支付商户号支持的主体类型为：**个体工商户、企业、事业单位、政府机关、社会组织**。个人主体不在其列。

更前置的是：申请小程序支付权限要求账号先完成**微信认证**，而个人主体小程序无法进行微信认证。两道门都堵死。

> 来源：[微信支付商户文档中心 · 开发接入准备_小程序支付](https://pay.weixin.qq.com/doc/v3/merchant/4015459512)、[mchid与appid申请_通用规则](https://pay.weixin.qq.com/doc/v3/merchant/4012071573)

**影响**：个人主体版本连打赏都做不了。要收任何形式的钱，最低门槛是注册**个体工商户**。

**补充风险**：微信开放社区有开发者反映，个体工商户在**虚拟支付**（订阅制、虚拟商品）上仍受限，可能要求企业主体。若最终商业模式是订阅制，需要在注册个体工商户**之前**单独核实这一条，避免注册完才发现不够用。此条尚未取得官方文档的确定答复，标记为**待核实**。

### 2. 类目上有一条免资质的干净路径：工具 > 字典

个人主体开放的「工具」类目下包含以下**无需任何资质**的三级类目：

| 类目 | 官方适用范围 |
| --- | --- |
| **字典** | 适用于提供字典查询工具等服务 |
| 信息查询 | 适用于提供信息查询功能 |
| 效率 | 适用于提供日常生活、工作效率提升类服务 |

「**字典**」与本产品的形态高度吻合，是首选申报类目。

> 来源：[微信开放文档 · 小程序开放的服务类目](https://developers.weixin.qq.com/miniprogram/product/material)，"个人主体小程序开放的服务类目 → 工具"章节

### 3. 不能以教育或内容平台身份申报

- 个人主体的「教育服务 > 教育信息展示」虽然可选，但官方明确注明**不支持教育视频播放/直播、课程产品销售**。
- ICP 备案的服务内容分类中，「教育」大类对个人主体标注为**"不建议选择"**，「工具」则是**"可选，符合个人性质"**。
- 「网络图书」（含电子书、网络小说在线阅读）需要《网络出版服务许可证》。

> 来源：[微信开放文档 · 小程序备案服务内容标识选择指引](https://developers.weixin.qq.com/miniprogram/product/record/record_review.html)

**影响**：这条约束把产品形态**锁定为"用户自带文本的加工工具"**，不能做内置文章库的内容平台。

### 4. 强制 ICP 备案，且服务器必须在大陆境内

- 所有境内运营的小程序（含个人主体）**均须完成 ICP 备案**，未备案无法上线。
- 时限：小程序注册后 **20 个自然日内**完成备案。
- 服务器必须位于**中国大陆境内**且已实名认证；域名持有者信息须与小程序主体一致。香港/海外服务器无法备案。
- 需人脸活体核验。

> 来源：[微信开放文档 · 小程序备案常见问答](https://developers.weixin.qq.com/miniprogram/product/record/record_faq)

**影响**：如果后端要调用境外模型 API，需要额外的合规设计；用国内模型服务商（DeepSeek / 通义 / 豆包）是更稳的路径。

### 5. 包体积：词库绝无可能内置

- 主包 ≤ **2MB**
- 单个分包 ≤ **2MB**
- 总包 ≤ **30MB**（服务商代开发的小程序为 20MB）

> 来源：[微信开放文档 · 分包加载](https://developers.weixin.qq.com/miniprogram/dev/framework/subpackages.html)

**影响**：ECDICT 词库解压后 **903MB**（实测），比总包上限大 30 倍。词典查询**必须**放在服务端，小程序端只能是纯展示客户端。这反过来印证了"引擎与载体分离"的架构是对的。

### 6. AI 能力对外宣称可能触发算法备案要求（待核实）

抖音开放平台的个人主体类目文档明确要求：个人主体的「AI 工具」类目**仅支持调用第三方算法服务**，且需提供第三方算法服务的《互联网信息服务算法备案》截图、备案公示内容、以及与算法服务方的合同协议公示。

> 来源：[抖音开放平台 · 个人主体开放服务类目](https://developer.open-douyin.com/docs/resource/zh-CN/mini-app/operation/service-category/available-service-categories)

**微信侧未直接核实到等价条款**，标记为**待核实**。

**规避建议**：产品对外定位为「字典 / 阅读辅助工具」，不以"AI"作为卖点或功能名称。模型只在后台生成注释，不提供对话式 AI 交互界面。这样按「工具 > 字典」申报的把握更大。若未来要主打 AI 能力，需重新核实微信的算法备案要求。

## 三、内容版权：约束反而指明了正确形态

若内置外刊、新闻、书籍等英文内容库：

- 个人主体既无内容版权，也无《网络出版服务许可证》
- 属于第 3 条明令需要资质的范围

**结论：产品必须做成"用户自带文本、工具负责加工"。**

这不是妥协，而是三重收益：

1. 版权风险归零
2. 与「工具 > 字典」类目严丝合缝
3. 服务端**只缓存标注结果，不存储原文全文**（见开发文档的缓存设计），进一步远离复制权争议

## 四、竞品：切口是真实存在的

| 产品 | 交互范式 | 标注依据 | 覆盖层次 | 定价 |
| --- | --- | --- | --- | --- |
| LingQ | 点击查词 + 色彩标记已知/学习中/新词 | 个人已知词库 | 词汇 | 约 $72 / 半年 |
| Readlang | 点击即译（浏览器扩展） | 无个性化模型 | 词汇 | 免费 + 付费档 |
| 扇贝阅读 | 自动标注生词 + 即点即查 | **考纲词表**（四六级/考研） | 词汇 | 订阅制 |

三者的共同点是交互本质为 **reactive（点了才给）**。扇贝最接近本产品设想——它确实做自动标注——但两处关键差异：

1. **标注依据是考纲词表，不是个人词汇量模型**。四级词表对一个实际词汇量 12000 的读者毫无意义。
2. **只做词汇一层**。语法句式、习语、梗、文化背景完全没有覆盖。

**本产品的切口**：

- **Proactive（预判式）**：读之前注释已就位，眼睛不离开正文
- **个人词汇量模型驱动**，而非通用词表
- **四层覆盖**：词汇 / 习语搭配 / 语法句式 / 文化背景

第三点在几年前不成立（成本与模型能力都不够），现在成立了。这是时间窗口。

## 五、载体决策：为什么不先做小程序

### 与既有战略的冲突

根据 `life_os` 的核心战略「一个作品，两个出口」：用英文公开做一个产品，同时充当 OPC 现金流、求职作品集、英语训练场；收入须走 **Stripe / Paddle 等可开具收入证明的合规渠道**，因为它直接服务收入制签证的移民轨道。

微信小程序在这三项上均为零分：

| 战略目标 | 微信小程序的贡献 |
| --- | --- |
| 面向欧美用户的付费产品 | 0（用户是中文母语者） |
| 可证明的美元收入 | 0（人民币，且个人主体收不了钱） |
| 英文公开资产 | 0 |

### 自用场景下小程序是最差载体

若纯粹自用，小程序需要备案 20 天、过平台审核、受包体积限制、开发体验远逊于 Web。同样的功能，本地 Web 应用一个周末可跑通 v0。

### 采纳方案：引擎与载体分离

**核心引擎（分词 / 词典 / 个性化标注 / 模型标注生成）是载体无关的。**

```
                    ┌─────────────────┐
                    │   标注引擎 API   │  ← 全部核心价值在这里
                    └────────┬────────┘
                             │
        ┌────────────────────┼────────────────────┐
        │                    │                    │
   Web 前端            浏览器扩展            微信小程序
  （立即自用）        （V2，真沉浸）      （可选分发通道）
  （可接 Stripe）
```

**第一阶段只做：引擎 + Web 前端。** 立即自用，且未来接 Stripe 面向欧美用户、或接小程序客户端，引擎均不需重写。无论最终走哪条路，核心资产都不浪费。

**小程序推迟到什么时候做？** 满足以下任一条件时再启动：

- 确认要服务中文付费用户，且已注册个体工商户（否则收款为零）
- Web 版已验证核心体验成立，只是缺一个分发通道
